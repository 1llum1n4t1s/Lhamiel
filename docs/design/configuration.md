# Settings and secrets

1. The view model projects settings to the UI and saves through a 300 ms debounce. After the delay, it reads and applies the UI values together on the UI thread, then persists them in the background. Cancellation is checked both before applying values and before saving to discard pending updates cancelled during the delay or dispatcher wait by a newer change or shutdown flush.
2. Operation entry points flush pending UI changes and create a snapshot so an operation does not observe mid-flight setting changes.
3. Remembered compression passwords are DPAPI-protected for the current Windows user. Plaintext passwords exist only in short-lived scopes, are registered with log redaction, and have best-effort memory clearing.
4. The update base URL is a getter-only, non-serialized constant so settings files cannot redirect update traffic to another host.
5. The legacy `AddToContextMenu` value fills only missing `AddExtractToContextMenu` and `AddCompressToContextMenu` keys, preserving explicit new values, and the migrated shape is persisted after load.
6. `Settings.Load` falls back in three stages: `JsonSerializer.Deserialize`, then per-property recovery through `JsonDocument` (type-mismatched properties keep defaults), and only when nothing is recoverable, moving the corrupt file to `settings.json.corrupt_<timestamp>.bak` (Move; if that fails, a best-effort Copy to the same backup name, then Delete, then an atomic empty-JSON overwrite; the log names the stage that actually succeeded) and starting with defaults.
7. `CompressionPasswordSession` limits remembered plaintext to 1024 characters, zero-fills intermediate byte arrays with `CryptographicOperations.ZeroMemory` (best effort), and returns `null` when DPAPI decryption fails. Settings never wipe the stored blob automatically on that failure; the caller notifies the user and re-prompts, and the saved value is replaced only by a new accepted password or an explicit user clear.
8. A `settings.json` that exists but cannot be read (another process holds it exclusively, access is denied, or its attributes cannot be queried) is distinct from a missing file and from corrupt JSON. `Settings.LoadWithStatus` reports `Created` (missing; defaults written), `Loaded`, `CorruptReset` (only `JsonException`; quarantined as in item 6) or `Unreadable`; `Load()` keeps its signature and returns defaults for `Unreadable` so startup continues. Reads retry transient lock errors through `LockedFileRetryPolicy` for 3 attempts (about 0.1 s in total). The unreadable state never writes defaults over the file. `SettingsManager` that started `Unreadable` (or whose load threw) refuses every save with `InvalidOperationException` for the whole session, because the in-memory defaults cannot be told apart from user edits and writing them would erase all settings and the encrypted password; restarting reloads the real file. When the pre-save re-read is `Unreadable` (UI or archive worker), the save is aborted before the mutator runs, with the same exception type as a failed write, so existing failure handling (log or user notification) applies. `RefreshSavedCompressionPassword` keeps the current value when the file is unreadable. A UI session that started `Unreadable` shows one startup warning after the main window appears (never in CLI, worker, or silent-update runs) and refuses context-menu, file-association, icon-shortcut, and shortcut changes before touching external state. In that state `.lhaignore` initialization and the Velopack hook's context-menu refresh and icon restore are skipped; the icon-restore marker is kept for the next readable startup. `SettingsManager` restores the pre-mutation values under its lock when a mutating save fails.
